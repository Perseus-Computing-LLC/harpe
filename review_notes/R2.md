## Findings

### G1 (medium): the DTOC placeholder header carries `tool_name` and `scope` unescaped, so the parse reads back another sidecar

Test: `tests/review2_dtoc_placeholder_header_unescaped.py` (exit 1: 4 failed, control passed).

`CompressedToolOutput.format_placeholder` (`src/harpe/dtoc.py:49-72`) writes the header as space-separated
`key=value` tokens and puts `tool={self.tool_name}` (`:53`) and `scope={scope_val}` (`:60`) in verbatim.
`DynamicToolCompressor.parse_placeholder` (`:169-192`) does three things. It takes the header up to the first `]`
(`:173`), splits it on whitespace (`:176`), and lets a later `key=` token overwrite an earlier one (`:178-191`). So
when a tool name or scope holds a space or a `]`, the parse no longer matches the artifact:

- scope `"Acme Corp"` parses as `"Acme"` and tool `"Google Search"` as `"Google"`. That scope is the tenant or
  project isolation scope (`:32`).
- tool `"search]"` ends the header early, so `confidential`, `lines`, `bytes` and `scope` disappear from the parse
  of a confidential artifact.
- a scope of `"acme confidential=false"` overrides the artifact's `confidential=true`.
- a tool name containing `ref=dtoc_000000000000` replaces the artifact's `ref`, which is the handle `restore` takes.

H-R3's acceptance criterion is that the flag survives the compaction round trip
(`tests/test_dtoc_sidecar_hr34.py:1-6, 39-45` parse the placeholder back). The round-1 fix made `to_context_item`
write the typed sidecar over free metadata "matching the placeholder" (CHANGELOG `[Unreleased]`/Fixed). F5 closed
the free-metadata route by which a typed sidecar value gets replaced. The header is a sibling route and is still
open: free text in two typed fields rewrites the others. Severity is medium for the same reason as F5: nothing
inside harpe decides access from a parsed placeholder (the engine reads `ContextItem.sensitivity`), but any
consumer that reads the placeholder the documented way gets the wrong scope, flag or ref. The test accepts either
fix: refuse such names in `maybe_compress`, or encode them so the parse returns the artifact's own sidecar.

### G2 (medium): with hooks, `synthesize` copies items shallowly, so a hook's metadata edit is written into the caller's item

Test: `tests/review2_hook_copy_shares_caller_metadata.py` (exit 1: 2 failed, 2 controls passed).

`ContextBudgetEngine.synthesize` (`src/harpe/engine.py:511`) copies the items before the `pre_prune` hooks so that
hooks work on copies. `_count_uncounted` (`:366-376`) says "Hooks may change items in place, so with hooks every
item is copied", and the comment after the hooks says "Hooks work on copies and may reclassify or rewrite them"
(`:571-572`). The copy is `it.model_copy()` (`:374`, and `model_copy(update=...)` at `:372`). Pydantic makes that
copy shallow, so the copy's `metadata` is the caller's own dict.

The result depends on what the hook writes:

- A hook that sets a top-level field (`priority`, `sensitivity`) changes only its copy. This is the control.
- A hook that writes into `it.metadata` writes into the caller's item. That is where harpe reads `relevance`,
  `rrf_score` and `attention_density` (`:151-165`, and `:421-430` for `LEAST_RELEVANT`).

The edit outlives the call. In the test, a per-query relevance hook scores the items for one query. A later
hook-less `synthesize` over the same items then selects `trivia` instead of `runbook`, on scores the earlier hook
wrote. The copy exists to prevent this write, and it prevents it for scalar fields only. This is the same seam as
F2 (hooks on copies), on the nested fields. The test accepts any fix that leaves the caller's items as given.

### G3 (medium): `synthesize` refuses duplicate ids only before the `pre_prune` hooks

Test: `tests/review2_hook_duplicate_ids_not_refused.py` (exit 1: 1 failed, 2 controls passed).

`_normalise_items` (`src/harpe/engine.py:342-364`) refuses duplicate ids, on the grounds that "a report keyed by id
would still be ambiguous for the caller. Refuse them rather than guess" (`:358-359`, check at `:360-363`).
`synthesize` runs that check on the caller's items (`:562`) and then hands the items to the hooks (`:568-570`). The
round-1 fix re-runs the withholding decision and the token count after the hooks "so the items selected are the
items checked" (`:571-576`). It does not re-run the id check, so the id rule only holds for the items before the
hooks.

The ordinary trigger is a replayed turn:

1. A hook injects a standing item, here `reminder`.
2. Turn 1's report includes it.
3. Turn 2 is synthesized over turn 1's included items plus the new question.

The hook adds `reminder` a second time, and turn 2's report includes two items with that id, each charged to the
budget. If the caller passes the same duplicate itself, the call raises `ValueError` (the control). The test
accepts refusal or a report with unique ids. G4 is what this report does downstream.

### G4 (high): `TwoPassBuild` keys a report's rows by id without refusing a repeat, so its receipt misdescribes the context

Test: `tests/review2_two_pass_duplicate_ids_receipt_misdescribes.py` (exit 1: 1 failed, control passed).

The module promises that "the context the build hands out is always the one its receipt describes"
(`src/harpe/two_pass.py:11-12`). `TwoPassBuild.__init__` (`:153-162`) stores each included item in a dict keyed by
id (`_desc`/`_tier0`) but appends every occurrence to `_order`. A repeated id therefore overwrites the first row in
the dict and still appears twice in the order. As a result:

- `items()` (`:264-274`) hands out the row twice, and both copies are the last occurrence, so the first
  occurrence's content is lost.
- `rows_pass1` (`len(self._desc)`, `:245`) and `used_tokens` (`:191-193`) count the row once.
- The receipt `emit()` writes from `receipt_payload()` (`:277-288`) names 3 rows and 22 tokens, while the build
  hands the model 4 rows and 28 tokens.

Nothing refuses the repeat, because the row checks (`:164-184`) compare id sets only. On this head the engine
produces exactly such a report (G3). A `SynthesisReport` is also a public model that a caller, a stored report, or
a `post_prune` hook can build. This is the same guarantee round 1 rated high in F3, a receipt that does not describe
the context, reached through the build's input rather than through call order. The test is independent of G3 and
accepts refusal or a receipt that matches `items()`.

### G5 (high): DTOC refs are a 48-bit truncated hash, and the store overwrites on a ref match

Test: `tests/review2_dtoc_ref_truncated_hash_overwrite.py` (exit 1: 1 failed, control passed).

The round-1 fix escaped `\` and `:` in the tool name (`src/harpe/dtoc.py:223-226`). CHANGELOG `[Unreleased]`
("Digests and handles") claims that as a result "two different artifacts cannot share a ref and overwrite each
other's stored output". The escaping closes the structural witness only. The ref is still
`"dtoc_" + sha256(f"{safe_tool}:{output}").hexdigest()[:12]` (`:227-228`), which is 48 bits. `maybe_compress`
stores the artifact with `self._store[ref_id] = artifact` (`:257`), and `LRUArtifactStore.__setitem__` (`:96-106`)
replaces whatever is under that key without comparing payload, tool or sidecar.

A colliding pair needs only a birthday search of about 2^24 hashes, with no SHA-256 weakness involved. A
distinguished-point search in pure Python found the pair in the test in about 20 s and 4e7 hashes. It is two
`http_get` outputs that differ in a 12-hex request id and share ref `dtoc_8f0207e1b5f1`. One is a public status
page, compressed as not confidential; the other is a payroll page, compressed with `confidential=True`.

After both are compressed:

- `restore(public.ref_id)` returns the payroll output, and the public page's stored output is gone. That is the
  expansion the public placeholder (`:69-71`) tells the model to request, and that placeholder goes to a remote
  model.
- The two context items share the id `item_dtoc_8f0207e1b5f1` (`:285-286`).

Severity is high because it breaks integrity and loses data. The realistic attacker controls the text of two tool
outputs, for example two web pages, and swaps what a handle restores after its summary was seen. The confidential
variant is the same mechanism with a sensitive second artifact. Reaching a *given* confidential ref would need a
2^48 second preimage, so that variant is the less likely one. The test accepts any fix: refs that do not collide, a
store that refuses or disambiguates a ref that already holds different output, or refusing the second artifact.

## Suspected, unconfirmed

- **S1, DTOC store keeps one artifact per ref, and the ref ignores the sidecar** (`src/harpe/dtoc.py:223-228`,
  `:257`). Compressing the same tool output once with `confidential=True` and then again without it leaves the
  store holding the non-confidential artifact. No public API reads the stored sidecar today: `restore` returns
  only the payload (`:294-299`), and `to_context_item` takes the caller's own artifact (`:260-292`). So this
  cannot be shown through the public contract. It becomes a laundering path once anything reads the sidecar back
  from the store.
- **S2, one fence per compiled graph.** `StateGraph.compile()` returns a new `CompiledGraph` with its own fence
  (`src/harpe/state_graph.py:124`, `:159-160`). Two graphs compiled from one builder therefore do not share a
  high-water mark, and a holder superseded on one is admitted on the other. The docstrings define the fence per
  compiled graph (`:142`, `:201-206`), so this is a design note rather than a defect.
- **S3, `post_prune` output is not re-checked.** `post_prune` hooks get the report object that `synthesize` returns
  (`src/harpe/engine.py:639-641`), after the withholding decision and with no re-check. A `post_prune` hook that
  reclassifies or appends an included item therefore changes the returned report. The protocol calls this the
  "finalized report" (`src/harpe/protocols.py:26-28`), and no document promises that `post_prune` changes are
  checked, so this was not filed.
- **S4, a token equal to the high-water mark is admitted** (`src/harpe/state_graph.py:188`). A replayed copy of
  the current holder's token can therefore run alongside it. This is documented ("at least the newest token",
  `:201-202`) and is standard for fencing, so it is not a finding.
