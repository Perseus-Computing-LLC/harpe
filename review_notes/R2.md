# Review R2 — harpe @ 8cb368be5a6d

**Cut:** atomicity and crash consistency: what state is observable after a kill between any two syscalls of a
write path. Round 2, after the round-1 fix (commit 8cb368b, `git diff f6b32d4 HEAD -- src`).

**Scope:** `src/harpe/*.py` at detached HEAD `8cb368be5a6d`. Priority went to the fix diff (`two_pass.py`,
`profile.py`, `state_ledger.py`, `compression_vllm.py`, `dtoc.py`) and to `tests/test_crash_consistency.py`. The
Argus writer the receipt goes through (`argus_ledger/ledger.py`, `canonical.py` in the suite venv) was read as
context. Threat model: `SECURITY.md:18-21`. Harpe runs in-process and has no network code. Its only durable write is
the `harpe.context_built` receipt (`src/harpe/two_pass.py:113-115` → `AppendOnlyLedger.append`). Every other write
path is an in-memory multi-step mutation. A kill there destroys the object, so an exception raised between two
steps stands in for the crash.

**Method:** each finding is one `tests/review2_<name>.py`. Each was run alone with the brief's exact command
(`env -u KIBISIS_PASSPHRASE -u KIBISIS_PASSPHRASE_FILE -u KIBISIS_SRC -u CI PYTHONPATH=src
/opt/data/work/telarch-suite/.venv/bin/python -m pytest -q -p no:cacheprovider <file>`) and exited 1 on its
intended assertion while its control passed. Nothing under `src/`, `bindings/` or the existing tests was edited.

## Findings

### H1 (medium): `TwoPassBuild.emit()` seals the build for good when Argus refuses the receipt before writing anything

Test: `tests/review2_two_pass_refused_emit_seals_forever.py`. Observed `3 failed, 1 passed`, exit 1.

The fix splits the receipt write into a checking step and a writing step. `_prepared_context_built`
(`src/harpe/two_pass.py:98-117`) checks, and returns `write()` (`:113-115`). `emit` sets `self._sealed = True`
(`:345`) between the two, then calls `write()` (`:346`). Three documents promise that a refusal which writes
nothing leaves the build open:

- `_prepared_context_built`'s docstring (`:100-103`): "Every refusal (payload, path, actor, a missing
  `argus_ledger`) raises here, before any byte is written, so a caller can tell a receipt that was never attempted
  from one whose write began".
- `emit`'s docstring (`:336-337`).
- CHANGELOG `[Unreleased]` (`CHANGELOG.md:18-19`): "Refusals that write nothing (a bad ledger path or actor, …)
  still leave the build open".

Harpe's own checks are weaker than the gates Argus applies inside `write()`. Argus applies them before it opens the
file (argus `ledger.py:447-451`: `validate_identifiers`, `validate_payload`; `canonical.py:59-79`, `:129`), or they
fail at its first syscall (`ledger.py:406`, `os.open`). The test hits three such refusals:

- **Actor `"harpe agent"`.** Harpe checks only for a non-empty str (`two_pass.py:106-107`). Argus raises
  `IdentifierError` because the actor contains whitespace.
- **`budget_tokens = 2**53`.** `__init__` accepts any int >= 0 (`:165-168`) and `_check_payload` checks only
  `type(value) is int` (`:84`). Argus raises `IntegerRangeError` because the value exceeds 2**53-1.
- **A `ledger_path` naming an existing directory.** `_check_ledger_path` (`:89-95`) accepts it, and Argus's
  `os.open(..., O_RDWR)` raises `IsADirectoryError`.

The state after each refusal:

- The ledger holds nothing. The test checks this precondition.
- `build.sealed` is True and `receipt_sequence` is None.
- `request()` and every later `emit()` raise "an earlier emit() … failed while writing its receipt, which may be in
  the ledger" (`:326-330`). That message is false here.
- `items()` still hands out the context.

So a context is in use that has no receipt and can never get one. Telling "never attempted" from "write began" was
the fix's stated contract, and these three refusals break it. The fix closed the "unsealed with a receipt" state
(R1 F1) but opened "sealed with no receipt" for refusals. Severity is medium, not high: no false or duplicate
receipt can result, and the trigger is a realistic misuse (an actor with a space, a mistyped path, an outsized
budget) that leaves the audit receipt missing. The test accepts any fix that keeps such a refusal out of the
sealed state, for example applying Argus's identifier, integer-range and path checks in `_prepared_context_built`.

### H2 (low): `DuoAttentionKVCacheManager.append_token` counts the token before sizing it

Test: `tests/review2_duo_append_token_counts_failed_token.py`. Observed `2 failed, 1 passed`, exit 1.

The fix reordered `allocate_sequence` (`src/harpe/compression_vllm.py:433-437`) to "size first: a prompt length
the sizing rejects leaves no half-registered sequence behind", and `tests/test_crash_consistency.py:173-182` holds
it to that. The sibling write path in the same class keeps the old order. `append_token` (`:439-444`) does
`generated_tokens += 1` (`:442`) and only then calls `compute_sequence_vram_bytes` (`:444`).

If the sizing raises, the caller is told the append failed, but the sequence already counts the token. A retry
then leaves `generated_tokens == 2` for one token, and every later sizing over-reports that sequence's VRAM. The
test shows this two ways:

- with `compute_sequence_vram_bytes` monkeypatched to raise, as the project's own test does;
- with no monkeypatch: the prompt `2**1022 - 2**968 - 1` sizes to `DBL_MAX`, and one more token makes the float
  `inf`, so `int(inf)` raises `OverflowError` (`:423`).

Severity is low: the class is a simulator, and the natural trigger needs an absurd length.

### H3 (low): fix regression — a negative `prompt_tokens` makes `PagedKVCacheManager.allocate_sequence` take every free block but one

Test: `tests/review2_paged_negative_prompt_takes_pool.py`. Observed `1 failed, 1 passed`, exit 1.

The pre-fix loop was `for _ in range(needed_blocks)`, which takes nothing when `needed_blocks <= 0`. The fix plans
over `self.free_blocks[:needed_blocks]` (`src/harpe/compression_vllm.py:211`) and commits with
`del self.free_blocks[:needed_blocks]` (`:217`). For `prompt_tokens=-20`, `needed_blocks = ceil(-20/16) = -1`
(`:201`), so the capacity check `len(free) < -1` (`:202`) passes and the slice `[:-1]` is every free block but the
last.

On a 10-block pool one call has these effects:

- it takes 9 blocks;
- it stores `num_tokens_stored = -20` (`:220`), because `PhysicalBlock` does not validate assignment;
- `compute_fragmentation_stats` reports utilization -12.5% and internal fragmentation 113.89%;
- a following 32-token sequence is refused with `MemoryError`.

The fix's own comment (`:208`) says "a failure mid-plan leaks no block", yet this input leaks almost the whole
pool with no failure at all. The pre-fix code (checked against `git show f6b32d4:src/harpe/compression_vllm.py`)
returned `[]` and took nothing. Severity is low: it is a simulator and needs an invalid count. The test accepts
refusing the prompt or taking no block.

## `tests/test_crash_consistency.py` vs the round-1 finding tests

- **R1 F1 (two-pass seal).** The new test `test_an_emit_whose_write_raises_keeps_the_build_sealed`
  (`tests/test_crash_consistency.py:60-79`) replaces `AppendOnlyLedger.append` wholesale, so no record ever
  reaches the file. It never exercises the actual F1 window, where the record is on disk and the append then
  raises (fsync plus a failed rollback, or EIO from `close`). That coverage still comes only from
  `tests/review1_two_pass_emit_crash_unsealed.py`. The new test also fixes "a write that raised having written
  nothing ⇒ sealed" as the contract. That is defensible when the failure point is unknown, but the same code path
  produces H1 for refusals that harpe could check up front. The test is weaker than the R1 test but does not
  contradict it.
- **R1 F2 (profile).** `test_profile_add_crash_in_the_parse_leaves_the_latest_session` (`:119-130`) is equivalent to
  the R1 test. The arrival-position and wrong-type tests (`:88-111`) go further.
- **R1 F3 (state ledger).** `test_state_ledger_failed_batch_records_nothing_and_retry_pairs_once` (`:139-148`)
  asserts what the R1 test asserts: the batch is all or nothing, and a retry pairs once.

Nothing was found that asserts weaker behaviour than a round-1 finding in a way a red test could show.

## Suspected, unconfirmed

- **"Make a new build" after an unacknowledged receipt.** After R1 F1(a), the record stays in the file while Argus
  says it is not acknowledged. The seal message (`src/harpe/two_pass.py:329-330`) tells the caller to make a new
  build to write another receipt. If the caller rebuilds the same context, the ledger then holds two
  `harpe.context_built` records for it, from two builds. The "one receipt per build" contract is per build, so
  this was not filed.
- **Transient pre-write failures seal the build too.** EMFILE at `os.open`, EINTR or ENOLCK at `flock`, or a
  corrupted tail that Argus refuses (`LedgerCorruptionError`, argus `ledger.py:470-482`) all fail before any byte
  is written, yet they seal the build like H1's refusals. Harpe cannot tell these failures apart from a write
  that raised after writing without help from Argus, so "seal" is the conservative choice. Not filed.
- **Mixed arrival and given orders in `ProfileLedger`.** Take an arrival-ordered turn (`(0,)`) followed by a turn
  with `order=("s2", 0)` while `latest_order` is None. The comparison guarding `moves_latest`
  (`src/harpe/profile.py:677`) is skipped, so the statement is committed. Every later `statements()` call then
  raises `TypeError` from the sort (`:725-728`). The docstring forbids mixing the two kinds of order (`:668-670`).
  Not filed as a crash-consistency defect.
- **`post_prune` hook fan-out** (`src/harpe/engine.py:705-706`). Carried over from R1, still not atomic, and no
  contract promises atomicity.

## Checked, no finding

- `TwoPassBuild.request` (`src/harpe/two_pass.py:245-266`): it checks the seal under the lock, and no step between
  `_used` and `_expanded` can raise. The seal is set only after every harpe-side check (`:344-345`), and the R1 F1
  windows (durable record, then a raise) now stay sealed.
- `ProfileLedger.add` (`src/harpe/profile.py:675-690`): the turn is read in `_read_turn` (`:692-722`) without
  touching the ledger. The commit steps (`:683-689`) cannot raise, because the attribute keys come from
  `self.specs` and the comparisons happen before the commit.
- `StateLedger.add` and `add_units` (`src/harpe/state_ledger.py`): claims are staged, then committed with one
  `extend`, and `seq` numbering is computed from the staged length.
- `DynamicToolCompressor.maybe_compress` (`src/harpe/dtoc.py:317-319`): the placeholder is rendered before the
  store. `LRUArtifactStore.__setitem__` (`:136-146`) has no raising step for `CompressedToolOutput` values.
- `PagedKVCacheManager.append_token` and `free_sequence` (`src/harpe/compression_vllm.py:226-270`): pure
  attribute and list operations with no raising step between them. `CompiledGraph.invoke` (run state is a local
  deep copy) and `AgentSelfHistoryTracker`, `OpenLoopTracker` and `SuppressionController` (one dict or list store
  each; pydantic models without `validate_assignment`) were also checked.
