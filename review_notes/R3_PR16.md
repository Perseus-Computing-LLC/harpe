### H1 (medium): a `pre_prune` hook that rewrites content keeps the pre-hook token count (F2 class not closed for cost)
`tests/rv1110_hook_rewrite_keeps_stale_token_count.py`. Observed exit 1: 1 failed, 1 control passed.

`src/harpe/engine.py:576` counts every item before the hooks; the post-hook re-count (`:589`, `_count_uncounted`
`:370-383`) only touches items with `token_count <= 0`. The comment at `:582-584` says "what each item costs
[is] decided again on the items they left, so the items selected are the items checked". It is not: five items a
hook expanded to ~800 tokens each are all included against `available_context` < 1000, and the report says
`consumed_tokens` = the pre-hook sum (a separate two-item probe: reported 6, actual 5005). Sensitivity is re-checked after hooks (the
F2 witness); cost is the sibling field R1 listed as suspected. Violates SECURITY.md Scope: "Unpinned items are
added only while they fit the budget's available context." and makes its advice "Check `consumed_tokens` if you
need a hard cap." unusable, because `consumed_tokens` is the stale sum.
Not a regression: 723ff5b and 044ea15 give the same numbers. It is incomplete closure, and the new comment
asserts the opposite of what the code does.
Fix direction: remember `(content, token_count)` per item before the hooks and re-count any item whose content
changed and whose count the hook left untouched (a hook that sets its own count keeps it).

### H2 (medium): regression in a02a145: with a hook registered, `synthesize` raises `TypeError` on metadata `deepcopy` cannot copy
`tests/rv1110_hook_deepcopy_breaks_uncopyable_metadata.py`. Observed exit 1: 2 failed, 3 controls passed.

`src/harpe/engine.py:375-381` (`model_copy(deep=True)` for every item when hooks are set) and `:579` (withheld
items). `ContextItem.metadata` is `Dict[str, Any]`, "Arbitrary item metadata" (`models.py:99`). A lock, an open
handle or a client object in metadata now makes `synthesize` raise `TypeError: cannot pickle '_thread.lock' object`;
at 044ea15 (shallow `model_copy()`) and at 723ff5b the same call returned a report, and it still does when no hook
is registered. Registering a no-op observer hook is enough. The last test in the file pins G2 so a replacement
(copy the metadata containers, share opaque leaves; or fall back per value when deepcopy raises) cannot reopen it.
Severity is a judgement: it is a new exception on input that used to work, not a wrong selection.

### H3 (medium): regression in the round-1 fix: `TwoPassBuild` raises `TypeError` on the same metadata, no hook needed
`tests/rv1110_two_pass_deepcopy_breaks_uncopyable_metadata.py`. Observed exit 1: 1 failed, 2 controls passed.

`src/harpe/two_pass.py:205-214` (`_counted`: `model_copy(deep=True)` for every item and row the build is given)
and `:281` (every item again on every `items()` call). Same cause as H2 at another entry point and from another
commit: the build worked on such a report at 723ff5b and at 2a43c31 and raises at 044ea15 and 1451dc4. Here every
caller is affected, with or without hooks. The third test pins the property the copies were added for (F3: the
build owns what its receipt accounts for).
One fix serves H2 and H3: a copy that owns `metadata`'s dicts and lists and shares the leaves. Measured on 10,000
items it is also faster than `deepcopy` (see Performance).

### H4 (low, task E): a lone surrogate in text raises `UnicodeEncodeError` from `maybe_compress` and from `synthesize` when the item is pinned
`tests/rv1110_lone_surrogate_breaks_hashing_paths.py`. Observed exit 1: 2 failed, 2 controls passed.

Strict `.encode("utf-8")` at `src/harpe/dtoc.py:264` and `:277`, `src/harpe/engine.py:109`,
`src/harpe/two_pass.py:65`. `json.loads` of an escaped emoji cut in half by truncation yields such a str.

unpinned and raises on it pinned. Same behaviour at 723ff5b: not introduced by this PR.

Repeated work:

- Re-tokenizing: `synthesize` writes counts onto its own copies, never back to the caller's items, so uncounted
  items are tokenized again on every call. Five calls over the same 10,000 uncounted items: 2,099 ms; over
  counted items: 50 ms.
- Two regex passes per item in `count_tokens`: pieces 227 ms + hex runs 121 ms at 10,000 items.
- Deep copies (this PR): 117 ms for 10,000 items with light metadata, 461 ms with a 256-float list each, against
  15 ms for shallow copies. `TwoPassBuild.items()` deep-copies every item on every call (not measured).
- Sorting: cProfile shows 2 `sorted` calls per `synthesize` (3 for KNAPSACK_DP). Outside the greedy sort key
  (`engine.py:303`) they cost under 3 ms at 10,000 items. Whether one list is sorted twice was not checked.
- Error path: `_refuse_duplicate_ids` (`engine.py:367`) builds its message with `ids.count(i)` for every id. One
  duplicate among 10,000 / 20,000 / 40,000 items takes 0.62 / 2.26 / 10.0 s to raise. Present at 723ff5b; this PR
  added two more call sites (`engine.py:588`, `two_pass.py:154`).

Native path: `harpe_native` 0.1.0-alpha.11 is importable in this interpreter and enabled (`_native.enabled()` is
True). It exports only `exact_knapsack`. On the same instances it is 7.6x (500,100 cells: 5.8 vs 0.77 ms) to 11.4x
(5,000,000 cells: 79.7 vs 7.0 ms) faster than the Python DP, with identical selections. It is not used in the
measured configurations: at 500, 2,000 and 10,000 items with a 28,000-token budget, `n * (capacity + 1)` exceeds
`max_cells` = 5,000,000 (`engine.py:289`), so `knapsack_solver` is `"greedy"` in all three. The exact path needs,
for example, at most 178 fitting items at this budget.

Proposed changes:

| # | change | measured or expected gain |
|---|---|---|
| 1 | Memoize `count_tokens` by content in `HeuristicTokenCounter` (bounded dict), or write counts back to the caller's items | Repeat calls over uncounted items: 344 ms -> 0.56 ms per 10,000 items (measured memo hit); 5 turns 2.1 s -> about 0.4 s |
| 2 | In `count_tokens`, look for hex runs only inside pieces of 8+ characters instead of a second pass over the text | 344 -> 265 ms at 10,000 items (-23%, measured; equal counts on 30,000 strings) |
| 3 | Replace `model_copy(deep=True)` (engine and two-pass) with a shallow copy plus a copy of `metadata`'s dicts and lists only | 117 -> 64 ms (light metadata), 461 -> 196 ms (embeddings) per 10,000 items, measured; also fixes H2 and H3 |
| 4 | `_refuse_duplicate_ids`: collect duplicates with `collections.Counter` | Error path 0.62 s -> under 5 ms at 10,000 items (expected; linear) |
| 5 | Greedy fallback: compute densities once into a list and sort indexes on it | Up to about 2x on the 6.7 ms solve at 10,000 items (expected) |
| 6 | Document that above `max_cells` the solver is greedy and the native kernel is idle, or raise `max_cells` when native is enabled (5,000,000 cells cost 7 ms native) | At 7 ms per 5 M cells, 50 M cells would be about 70 ms and 50 MB of keep flags: an exact answer for 1,785 items at this budget (expected, not measured) |

## Suspected, unconfirmed

- S1 (carried from R2): the DTOC store keeps one artifact per ref and the ref ignores the sidecar, so compressing
  the same output again without `confidential=True` replaces the stored confidential artifact
  (`src/harpe/dtoc.py:282-284`, `:313`). Round 2's fix kept this on purpose ("still refresh their own ref"). No
  public API reads the stored sidecar, so it cannot be shown through the library. The plugin touches `_store` directly (`/opt/data/plugins/harpe-engine/__init__.py:132`, `:456`);
  whether it reads a stored sidecar was not checked.
- S2 (carried from R2): the fence is per `CompiledGraph`. A second `compile()` of the same builder admits token 1
  after the first compiled graph ran under token 5 (probed). In-process only by design; nothing in SECURITY.md
  claims more.
- S3: `governor._is_revoked` (`src/harpe/governor.py:54`) is a substring test, now applied to history items as
  well. A history item whose `epistemic_state` is `"unrevoked"` or `"not revoked"` is reported as a contradiction;
  before round 1 only the exact `"revoked"` was. No list of valid states exists in the repo, so whether such a
  value is legitimate is not known.
- S4: `TwoPassBuild` accepts a build whose descriptions already exceed `budget_tokens` (probe: `used_tokens` 300
  against `budget_tokens` 120) and writes that into the receipt. The docstring calls the budget "the ceiling
  Pass 2 spends against"; whether construction should refuse is a design question.
- S5: `ContextBudgetEngine._knapsack_trace` is instance state read into the report (`engine.py:642`); two threads
  sharing an engine could report each other's `knapsack_solver`. Not probed.
- S6: `ProfileLedger.add` mixing turns with and without `order` compares arrival positions with caller orders;
  the docstring forbids it but nothing refuses it. Not probed.
