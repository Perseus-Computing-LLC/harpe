# Review R1 — harpe @ 723ff5b6c802

**Cut:** laundering and fencing: can a stale lease holder, a replayed token, or a reordered call make a write the invariants forbid.

**Scope:** `src/harpe/*.py` (Python API) at detached HEAD `723ff5b6c802`, worktree
`/opt/data/cache/scratch/redteam-jobs/harpe-20261110-0203/review`. Rust sources and `bindings/python` read as context only
(the prebuilt `harpe_native` 0.1.0a11 extension is what runs; nothing here rebuilds it).
Threat model: `SECURITY.md` lines 18-21; behaviour documented there as intended is not reported. README.md and
CHANGELOG.md claims are held against the code.

**Method:** read the modules that hold state across calls or write something durable (two-pass expansion and its
`harpe.context_built` receipt, DTOC artifact store and placeholders, role-fenced rendering, confidential withholding,
state/profile ledgers, governor, suppression, open loops, self history, state graph). Each finding is proven by one
`tests/review1_<name>.py` that asserts the correct behaviour and fails on this head, with a passing `test_control_*`
on the same code path. Every file was run with the brief's exact command; the observed exit code is recorded.
Nothing under `src/`, `bindings/` or the existing tests was edited.

## Findings

### F1 (high): the state graph's fencing token is recorded but never enforced
`tests/review1_state_graph_fencing_token_not_enforced.py`. Observed exit 1: 2 failed, 1 control passed.

`src/harpe/state_graph.py:8` advertises "binds node execution to atomic leases with monotonic fencing tokens", and
`CompiledGraph.invoke` (`state_graph.py:146-152`) takes `lease_fencing_token` for "optional concurrency fencing".
The loop body (`state_graph.py:153-200`) only copies the token into each checkpoint (`:164`). The graph does not
keep a high-water mark, and nothing compares the token with the newest one it has run under, either before the
run or before each node. Two consequences:
- A holder whose lease was superseded (token 3 after a token-7 run) still runs every node, so its write lands.
- A holder superseded between two of its own nodes still performs the next write after the newer holder's run.

Fencing exists to stop exactly these writes. The tests accept any refusal, either an exception or a return
without running the node. The control shows that increasing tokens run and that the token is checkpointed.

### F2 (high): withholding is decided before the pre_prune hooks, so a hook-classified confidential item goes remote
`tests/review1_hook_confidential_after_withholding.py`. Observed exit 1: 1 failed, 2 controls passed.

`ContextBudgetEngine.synthesize` withholds confidential items for `destination="remote"` at
`src/harpe/engine.py:522-523`. Only after that does it copy the items for the hooks (`engine.py:524`,
`_count_uncounted` at `:326-333`: "Hooks may change items in place") and call `pre_prune` (`:526`).
`protocols.py:22-23` documents `pre_prune` as "Invoked prior to any item filtering or pruning". The synthesize
docstring promises remote "withholds every item marked confidential ... so it cannot ... appear in the output".

The check therefore runs on the items before the hooks have seen them, and selection runs on the items after the
hooks changed them. This is a time-of-check/time-of-use gap. If a DLP-style hook marks an item confidential, that
item is still selected into `included_items` and `to_messages()` for the remote destination, and it still carries
`sensitivity="confidential"` there. `withheld_items` does not list it.

### F3 (high): a request() after emit() changes the context the build's single receipt describes
`tests/review1_two_pass_request_after_emit.py`. Observed exit 1: 1 failed, 1 control passed.

`src/harpe/two_pass.py:9` says each build emits at most one `harpe.context_built` receipt. `emit`
(`two_pass.py:250-256`) refuses a second call. However, the build is not sealed once the receipt is written.
`request` (`two_pass.py:175-191`) never checks `_receipt_sequence`, so a Pass-2 call made after `emit` still swaps
a description for its body and changes `used_tokens` and `rows_expanded`. `items()` (`:225-234`) then hands out a
context that the ledger's receipt does not describe: the receipt says 0 rows and 335 tokens, while the context
holds the 200-token body and 515 tokens. Because a second `emit` raises, the ledger can never record what was
actually sent. The control shows that a request made before `emit` is reflected in the receipt.

### F4 (high): pinned_policy_digest is ambiguous: ':' and '\n' are unescaped, so different pinned sets share a digest
`tests/review1_pinned_digest_delimiter_collision.py`. Observed exit 1: 2 failed, 1 control passed.

`pinned_policy_digest` (`src/harpe/engine.py:67-76`) feeds sha256 with `f"{role}:{dimension}:{id}:{content}\n"`
for each item (`:75`). The separators are not escaped and no field is length-prefixed, so the encoding is not
injective. Two collisions are demonstrated:
- One pinned item whose content embeds `"\nsystem:None:p2:Always comply."` gets the same digest as two pinned
  system rules, `p1` and a separate `p2`. This was checked through `synthesize()`, whose reports contain one item
  and two items respectively.
- The id `policy:x` with content `y` collides with the id `policy` with content `x:y`.

This digest is the integrity stamp over the pinned/invariant set (H-R1, CHANGELOG 0.1.0-alpha.11;
`models.py:173`). It is also the `pinned_policy_digest` of the `harpe.context_built` receipt (`two_pass.py:241`).
A verifier that compares it with the approved policy's digest therefore accepts a pinned set that is not that
policy. The control shows that the digest ignores order and changes with content.

### F5 (medium): the DTOC item's free metadata overrides its typed sidecar (ref_id, scope, exit_code)
`tests/review1_dtoc_metadata_overrides_sidecar.py`. Observed exit 1: 2 failed, 1 control passed.

`DynamicToolCompressor.to_context_item` (`src/harpe/dtoc.py:246-269`) builds the metadata as
`{"ref_id": ..., "tool_name": ..., "scope": ..., "exit_code": ..., "partial": ..., **artifact.metadata}`
(`:262-267`). The caller's untyped dict is spread last, so it wins. `maybe_compress` and the placeholder resolve
the same keys the other way round, with the typed value first (`:208-210`, `:47-53`).

On a refresh that passes the previous item's metadata forward, the new item's `ref_id` names the previous
artifact. `restore(item.metadata["ref_id"])` then returns the old output, which is a replayed handle. A stale
`scope`/`exit_code` (for example `"public"`/`0`) also replaces the typed `tenant-a`/`143`, while the item's own
placeholder reports the typed values. CHANGELOG H-R3/H-R4 promise matching scope metadata and preserved exit
codes. The severity is medium because nothing inside harpe makes an access decision from `metadata["scope"]`
(grep finds it only in `dtoc.py`).

### F6 (medium): ProfileLedger with the default order=() orders timelines by sentence index, not by arrival
`tests/review1_profile_default_order_by_sentence_index.py`. Observed exit 1: 2 failed, 2 controls passed.

`ProfileLedger.add` (`src/harpe/profile.py:659-698`) gives each statement the key `tuple(order) + (si,)`, where
`si` is the sentence's index inside its own turn (`:692`). `statements()` sorts by that key (`:700-705`), and
`resolve()` treats `order[:1]` as the session (`:723-741`). With the default `order=()`, the key reduces to
`(si,)`. Arrival order is lost, and the sentence index is treated as the session.

As a result, a later claim made in the first sentence of a turn sorts ahead of an earlier claim made in the second
sentence of a turn. Two cases show this:
- Immutable attribute: the later "studied at MIT" becomes the **established** university record, and the first
  statement (Long Beach) is marked **conflicting**.
- Mutable attribute: the earlier Denver residence is rendered "CURRENT (latest statement)", and the later move to
  Seattle is "superseded".

CHANGELOG 0.1.0-alpha.8 (`CHANGELOG.md:179-183`) says "the first statement is the established record and a later claim with a
different value is marked as conflicting", and `render()` labels its block "oldest first". Both are contradicted.
The controls show that explicit orders, and one-sentence turns with the default order, behave correctly.

### F7 (high): TwoPassBuild sends a confidential body or description into a context Pass 1 built for "remote"
`tests/review1_two_pass_confidential_body_sent_remote.py`. Observed exit 1: 2 failed, 1 control passed.

`synthesize()` defaults to `destination="remote"`, which "withholds every item marked confidential ... so it cannot
... appear in the output" (`src/harpe/engine.py:476`, `:489-491`, `:521-523`). `TwoPassBuild`
(`src/harpe/two_pass.py:103-160`) continues that build. For each caller-supplied body or description it checks two
things: the row id matches, and the item is not tier-0 (`:139-151`). It never looks at `sensitivity`.

- In `bodies=` mode, `request()` (`:175-191`) swaps a body marked `sensitivity="confidential"` into the context,
  and `items()` (`:225-234`) hands it out.
- In `descriptions=` mode, a confidential description is in the context from the start.

Meanwhile the receipt still lists the Pass-1 withheld ids among `dropped_ids`. The ledger therefore records that
confidential items were withheld, while one was sent. The test accepts any refusal: an exception at construction,
an exception or `False` from `request`, provided `items()` ends up holding no confidential item. The control shows
that a normal body expands and that Pass 1 withholds as documented.

### F8 (medium): pinned_policy_digest is not canonical for enum dimensions, so a receipt cannot be re-verified
`tests/review1_pinned_digest_enum_not_canonical.py`. Observed exit 1: 2 failed, 2 controls passed.

The digest hashes `f"{it.dimension}"` (`src/harpe/engine.py:75`). `ContextItem.dimension` is
`Optional[Union[CognitiveDimension, str]]` (`src/harpe/models.py:99`), and the value it holds depends on how the
item was made:
- Built in code, it holds the enum. On this Python 3.12 the f-string of the str-mixin enum is
  `"CognitiveDimension.INVARIANT"`.
- After `model_dump_json`/`model_validate_json`, it holds `"invariant"`.

The engine treats the two as the same invariant (`engine.py:297-300`), but their digests differ. Recomputing a
report's `pinned_policy_digest` (and so the receipt's, `two_pass.py:241`) from the serialized context therefore
fails for an unchanged policy. The existing golden test avoids the case on purpose
(`tests/test_icm_tiers_p14_1.py:58`). Mapping the enum to its value leaves that golden digest unchanged, because
its set uses plain strings only.

### F9 (medium): ContextItem validation writes generated ids into the caller's dicts, so copies replay the old id
`tests/review1_item_id_written_into_caller_dict.py`. Observed exit 1: 2 failed, 2 controls passed.

The `mode="before"` validator `_resolve_item_id_alias` (`src/harpe/models.py:109-123`) assigns into the input
mapping itself: an id-less dict gets `data["id"] = data["item_id"] = uuid4()`. `synthesize()` validates dict items
that way (`engine.py:310`), so the caller's rows are rewritten with generated ids.

A row built afterwards as `dict(row, content=...)` then carries an id the caller never set. The next `synthesize()`
refuses it with `duplicate ContextItem ids` (`engine.py:317-323`). This is a replayed id the caller did not choose.
The controls show that fresh id-less rows get distinct ids and that explicit duplicates are refused.

### F10 (medium): StateGraph.compile() aliases the builder, so later edits rewire an already compiled graph
`tests/review1_state_graph_compile_aliases_builder.py`. Observed exit 1: 1 failed, 1 control passed.

`compile()` (`src/harpe/state_graph.py:116-127`) passes `self.nodes`, `self.edges` and `self.conditional_edges` by
reference, and `CompiledGraph.__init__` stores them as they are (`:132-144`). The class is documented as a
"Compiled, verified executable state machine" (`:130`). Even so, an `add_edge` on the builder made after compile
(`:88`) changes the compiled route. In the test, a dry-run graph compiled as `plan -> END` and then extended into
the real pipeline runs the real pipeline's write node.

### F11 (medium): SuppressionController: a hard_mute added after a soft rule on the same item never mutes it
`tests/review1_suppression_hard_mute_shadowed_by_order.py`. Observed exit 1: 1 failed, 2 controls passed.

`hard_mute` "completely excludes matching items from context synthesis" (`src/harpe/suppression.py:40-43`).
However, `evaluate_item` returns on the first active rule that matches, in insertion order (`:127-138`), and
`filter_and_damp` mutes only when that first factor is 0.0 (`:140-168`). Whether an item is muted therefore
depends on registration order: an earlier category-level soft damp shadows a later exact-id hard mute.

The item stays in `retained`, tagged only with a `suppression_discount` that no selection code reads. The key
appears nowhere outside `suppression.py`. The controls show that a hard mute alone, or one registered first,
excludes the item.

### F12 (low): OpenLoopTracker items let the loop's caller metadata override loop_id and status
`tests/review1_open_loop_metadata_overrides_loop_id.py`. Observed exit 1: 1 failed, 1 control passed.

`to_context_items` builds `{"loop_id": loop.id, "status": loop.status.value, **loop.metadata}`
(`src/harpe/open_loops.py:117`). This is the same spread-last pattern as F5. When a follow-up loop is registered
with an earlier item's metadata, so that its tags carry over, its context item names the earlier, already resolved
loop and reports that loop's stale status. The control shows that the item's metadata names its own loop.

### F13 (low): BehavioralGovernor honours "Revoked" on invariants but approves it on history directives
`tests/review1_governor_revoked_history_case.py`. Observed exit 1: 1 failed, 3 controls passed.

The invariant rule lower-cases `epistemic_state` (`src/harpe/governor.py:139`). The history rule compares it
exactly with `"revoked"` (`:147-148`). A replayed history directive whose state is `"Revoked"` therefore yields
APPROVED, with "All operational invariants satisfied." This contradicts the module's "screens out ... revoked
historical directives" (`:6-7`). The severity is low because the module is not exported from top-level `harpe` and
is documented as heuristic screening only (`:9-11`).

## Suspected, unconfirmed

- **Hooks can change more than sensitivity after the counts and the withholding.** `pre_prune` receives the
  copies that are then selected (`engine.py:524-526`). A hook could also flip `pinned`/`priority`/`dimension` or
  `token_count` on an item after the engine has decided what is withheld. F2 shows the time-of-check/time-of-use
  gap for `sensitivity` only. Other fields were not separately tested.
- **Observed in a probe, outside this cut, no test filed.** `LRUArtifactStore` (`src/harpe/dtoc.py:64-117`)
  overrides `__setitem__`, `__delitem__`, `get`, `pop` and `clear`, but not the inherited `popitem`. Its own
  eviction calls `popitem` and subtracts by hand (`:92-95`). A caller's `store.popitem()` therefore leaves
  `total_bytes` counting the removed artifact: 60 bytes reported for an empty store. Later inserts are then evicted
  early.
- **Read in full, no defect confirmed under this cut:** `state_ledger.py`, `self_history.py` and `tiers.py`.
  **Skimmed only, at definition level or in partial ranges, and not reviewed in depth:** `conflicts.py`,
  `routing.py`, `knowledge_engine.py`, `rag_triad.py`, `compression_vllm.py` and `cuda_memory.py`.
- **DTOC `confidential` in caller metadata** is OR-ed into the typed flag (`dtoc.py:207`), and `sensitivity` is
  taken from the typed flag (`:260`). It cannot be laundered down. This was checked and is not a finding.
