# Review R1 — harpe @ f6b32d467935

**Cut:** atomicity and crash consistency: what state is observable after a kill between any two syscalls of a
write path.

**Scope:** `src/harpe/*.py` at detached HEAD `f6b32d467935` (v0.1.0-alpha.13). The Rust sources (`src/*.rs`,
`bindings/python`) were read as context only. They have no write path: they hold a pure knapsack kernel and a lexical
ledger, with no I/O.
Threat model: `SECURITY.md` (Scope, lines 18-21). Harpe runs in-process and has no network code. Its only durable
write is the `harpe.context_built` receipt, which `two_pass.append_context_built` hands to
`argus_ledger.AppendOnlyLedger`. Every other "write path" is an in-memory multi-step mutation of a long-lived
object. For those, a kill between two syscalls is modelled as an exception raised between two steps.

**Method:** each finding is proven by one `tests/review1_<name>.py`. The test simulates the crash in-process, with
monkeypatched syscalls or a raising input. It then asserts the consistent post-crash state and fails on this head.
Every file was run alone with the brief's exact command. Nothing under `src/`, `bindings/` or the existing tests was
edited.

## Findings

### F1 (high): emit() seals the build only after append returns, so a crash after the receipt is durable leaves it unsealed
`tests/review1_two_pass_emit_crash_unsealed.py`. Observed exit 1: 3 failed, 1 control passed.

`src/harpe/two_pass.py:9-11` promises at most one `harpe.context_built` receipt per build, and says writing the
receipt seals the build. The only seal is `_receipt_sequence`, which `request` (`two_pass.py:229`) and `emit`
(`:306`) check. `emit` assigns it from the return value of `append_context_built` (`:308-309`), and that function
returns only after `AppendOnlyLedger.append` returns (`:106-107`). Any exception raised after the record reaches the
file therefore leaves a durable receipt with an unsealed build. Two such paths were exercised:

- (a) The record's `fsync` fails and the rollback `ftruncate` fails too. Argus then raises `LedgerCorruptionError`,
  which tells the caller not to assume nothing was written (argus `ledger.py:308-320`, `:532-541`). Harpe does not
  distinguish it from any other error.
- (b) The record is written and fsynced, and only the final `close()` in Argus's `finally` (`ledger.py:543-545`)
  reports EIO. Here the record is fully acknowledged on disk, yet `emit` raised and nothing is sealed.

What can then be observed:
- A retried `emit` appends a second `harpe.context_built` record (sequence 2) for the same build. One build now
  has two receipts.
- A `request()` after the failed `emit` still expands a row. `items()` then holds the 200-token body, while the
  receipt already on disk says `rows_expanded=0` and `used_tokens=335`. This reopens the rv1110 seal (old F3)
  through the crash window.

The kill window is the stretch between `os.write` of the record (argus `ledger.py:534`) and the assignment at
`two_pass.py:308`. A fix would mark the build as emitting, or poisoned, before calling `append`, and keep it
sealed whenever the append raised after it started writing. The control shows that a clean `emit` writes one
receipt and then refuses both `request` and a second `emit`.

### F2 (low): ProfileLedger.add() advances latest_order/latest_date before it parses, so a crashed ingest still becomes "the most recent session"
`tests/review1_profile_add_crash_moves_latest_order.py`. Observed exit 1: 1 failed, 1 control passed.

`ProfileLedger.add` updates `_arrivals`, `latest_order` and `latest_date` first (`src/harpe/profile.py:670-675`).
Only then does it split and match the turn (`:679-705`). The statements themselves are all-or-nothing, because they
are gathered in `found` and appended only at the end (`:706-709`). The "latest" bookkeeping is not. If ingest dies
anywhere after line 675 (a kill, a raising custom `AttributeSpec.value`, a `bytes` text), the ledger names that
turn's session as the most recent, although none of its statements are recorded. `render`/`_label`
(`:759-765`, `:793-796`) read `latest_order`. In the test, the Denver statement loses "CURRENT, stated in the most
recent session", and `latest_date` reports 2026-05-01, a date the ledger holds nothing for. A retry with the same
order heals it, because `(5, 0)` is not greater than `(5, 0)`. A caller that drops the failed turn keeps the stale
value. The severity is low: it is a label and metadata error, with no statement lost or invented.

### F3 (low): StateLedger.add_units() is not all-or-nothing, and the natural retry indexes the first units twice
`tests/review1_state_ledger_add_units_partial_batch.py`. Observed exit 1: 2 failed, 1 control passed.

`add_units` (`src/harpe/state_ledger.py:139-141`) sums `add` over the mapping, and `add` appends each claim as soon
as it is built (`:135-136`). If a later unit raises (here, a `datetime.date` that pydantic rejects in `Claim`), the
earlier units stay indexed, and the caller gets an exception instead of a count. Re-running the batch then indexes
`u1` twice, because `add` has no idempotence check on `unit_id`, and `conflicts_for_entity` returns the same pair
twice. The severity is low: the trigger is a type-annotation violation (`Mapping[str, Tuple[str, str]]`), and
`header()` dedupes by `(unit_id, text)` (`:205-211`), so the prompt path is unaffected.

## Suspected, unconfirmed

- **Argus chains onto a record it calls unacknowledged.** In F1(a), Argus's own message says "bytes from offset 0
  on are not an acknowledged record". The next `append` nevertheless accepts that complete line as the tail and
  writes sequence 2 after it (argus `ledger.py:457-484`). That is an Argus-side question, outside this repository,
  and is not filed here. Harpe's defect stands either way: the ledger ends up holding two receipts for one build.
- **post_prune hook fan-out is not atomic.** `synthesize` calls `post_prune` hook by hook (`engine.py:705-706`).
  If hook 2 raises, hook 1 has already seen and possibly persisted a report the caller never receives. This is
  inherent to the hook design, and no contract promises otherwise, so it is not filed.
- **KV-cache simulators** (`compression_vllm.py:196-220`, `:429-431`). `PagedKVCacheManager.allocate_sequence` pops
  free blocks one at a time before it records the table, so a kill mid-loop would leak blocks. No natural exception
  exists inside the loop, though, and the pre-check at `:202` covers capacity. `DuoAttentionKVCacheManager.allocate_sequence`
  registers the sequence before computing its size. Both are not proven red.
- **DTOC store.** `maybe_compress` inserts into the store, which may evict other artifacts, before it renders the
  placeholder (`dtoc.py:317-318`). No input was found that makes `format_placeholder` raise once the pydantic
  model has validated, so this is not filed. `LRUArtifactStore.__setitem__` (`dtoc.py:136-146`) has no failure
  point between its count and its insert for `CompressedToolOutput` values.
- **Checked and consistent under this cut:** `TwoPassBuild.request` (`two_pass.py:228-242`, all arithmetic under the
  lock, no raising step between `_used` and `_expanded`). Also consistent: `CompiledGraph.invoke`, whose working
  state is local and discarded on any raise (`state_graph.py:207-257`), and whose high-water mark is advanced at
  admission, as fencing requires. `AgentSelfHistoryTracker.record_action`, `OpenLoopTracker`,
  `SuppressionController.add_rule` and `revoke_rule` each build the object, then perform a single dict or list
  store. The Rust crate has no write path.
